1. Purpose and scope of the prototype
The prototype is a small, working version of the two-agent system in the job specification. It keeps the rules that
matter most: answers come only from approved content, changes need a named approver, every action is
logged, and guest messaging is refused. It uses mock data for the property management system and the
booking channels, and does not connect to real payment or booking systems.
What the prototype does
• Answers website visitor questions from approved knowledge-base files, citing the file used. If the answer is
not in those files, it offers a hand-off to a person and does not guess.
• Allows five free visitor messages, then asks the visitor to register. The count is kept on the server.
• Compares rates between a mock property system and a mock booking channel, and reports each difference
as a gap.
• Proposes a rate change. Nothing changes until a named person approves it; the change is then applied and
re-read to verify it.
• Keeps a change log that the application cannot edit or delete.
• Refuses any request to message, email or contact a guest, and logs the refusal. No messaging tool exists.
What the prototype does not do
• Connect to a real property management system, booking channel, billing system or payment provider.
• Provide the Chrome extension, multiple approvers, roles, several languages, date changes or payment
requests.
• Use vector search. The approved knowledge base is loaded into the model's context.

The prototype runs two roles on the same runtime. Each role has its own model, its own tool list and its own
guardrails. The checks that decide whether something is allowed run in code, before and after the model. The
model only decides what to say and which allowed tool to request.

Agent loop rules (both roles)
• The loop stops after 8 model calls and returns a safe fallback reply.
• A tool request that is not on the allowlist, or whose input does not match its schema, returns an error to the
model and has no side effects.
• Each turn writes one traces row: model ID, tools called, token counts and elapsed time.
• The model never receives credentials, and the system prompt contains only approved content for the
project.

5. Trust boundaries and security
Figure 10. Trust boundaries. Visitor text and model output are untrusted. Every rule that matters is enforced in server code,
not in the prompt. AWS credentials are used only by the Bedrock client.
Security rules for the prototype
• Passwords are hashed with argon2 (or bcrypt if argon2 is not available). Passwords are never logged.
• Credentials and keys live in an AWS profile or environment variables, never in project files. The real .env file
is excluded from version control.
• Payment details, where they appear in mock reservations, are masked to the last four digits in every output
and log.
• Database access uses parameterised queries only.
• The change_log table is protected by database triggers, so the application cannot rewrite its own history.
• The Bedrock IAM permission is limited to model invocation.

11. Assumptions, limits and what comes after the
prototype
Assumptions (to confirm)
• [ASSUMPTION] Mock data stands in for the property management system and booking channels. Real
connectors are a later phase.
• [ASSUMPTION] The retrieval threshold, password length and transcript retention are defaults (see the
assumptions register in the docs folder).
• [ASSUMPTION] Local development is the default. A hosted demo is optional and needs a persistent volume
or another database.
• [ASSUMPTION] Claude models on Bedrock are available in the chosen region and enabled for the account.
Known limits of the prototype
• Clearing cookies starts a new visitor session, so the message limit can be reset this way. Accepted for the
prototype.
• No email verification after registration.
• A single approver per project. No roles.
• Only the rate-update change type is built. Date changes and payment requests are designed but not
implemented.
• Model cost depends on usage; Bedrock access and pricing must be checked before use.
After the prototype (not in scope)
• Real PMS connectors (API first, Playwright browser fallback), then real channel connectors.
• Chrome extension for the back-office chat and approval cards.
• Stripe test-mode checkout, upgrade, downgrade and cancellation.
• Vector search for larger knowledge bases; PostgreSQL with pgvector.
• Multiple approvers, roles, email verification, monitoring and alerting.
